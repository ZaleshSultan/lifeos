## 2. Сделай полноценную «Учёбу» (mobile-first Telegram Mini App)

Сохрани существующую структуру приложения и удобный интерфейс для маленького экрана. Все кнопки должны реально работать, а не быть заглушками. Разделы:

- **Сегодня**: первая пара (отдельно «первая онлайн» и «первая очная» при необходимости), время, аудитория/онлайн, преподаватель при наличии, полный день, задания/дедлайны, ближайшие контрольные, быстрые переходы. - **Задания (Assignments)**: список по каждому курсу с названием, типом, Moodle/источником, max points, earned points, статусом (new/submitted/graded/missing/overdue), датой/временем, ссылкой на источник и подробной карточкой. - **Дедлайны**: единый список из университетских источников, сохранённых assignments и ручных LifeOS entities; дедупликация по устойчивому source id, корректные статусы и точное локальное время. Если срока в силлабусе нет — не придумывай календарную дату из номера недели без начала триместра.
- **Оценки**: текущие оценки по каждому assessment, earned/max, источник и время обновления; ручной override **отдельно от синхронизированных данных** (с указанием, откуда результат). Не перезаписывай ручные значения при Moodle sync без согласованной политики приоритетов.
- **Калькулятор 70+**: целевой балл по умолчанию 70, редактируемая цель 0–100. Ввод и просмотр реальных/предполагаемых оценок отдельно по Assignment, Quiz, Midterm, Endterm, Final, Cisco certificate и произвольным компонентам. Оценки должны поддерживать разные максимумы: 15/30, 90/100 и т.д.; конвертируй `earned/max * 100` перед взвешиванием. Не подменяй `null/not graded` нулём. Выводи: уже гарантированную долю итога, прогноз по известным/ожидаемым данным, минимально необходимый балл по одному выбранному оставшемуся компоненту, режим «какие оценки нужны по нескольким оставшимся работам» с переменными сценариями и feasible min/max. Если >100 требуется — «математически недостижимо»; если уже достаточно — «цель достигнута при текущих допущениях». Объясняй формулу, что именно принято за 0, и какой процент итоговой оценки даёт каждый компонент. По мере изменения ввода пересчитывай мгновенно без запроса к серверу; изменения сохраняй через API.
- **Силлабусы**: по каждому курсу источник PDF, статус верификации, дерево ATT1/ATT2/Final, проценты/компоненты/суммы 100, редактор весов и компонентов для пользователя. Возможность загрузить новый PDF и создать новую версию схемы с подтверждением, не ломая исторические оценки. Если PDF разобран неоднозначно — показывай ручную проверку, а не произвольные числа.

## 4. Безошибочная математика и тестовые сценарии

Реализуй чистую тестируемую функцию расчёта, общую для UI и сервера или с одинаковыми тестовыми фикстурами. Пример: DBMS ATT1, Assignment1=90/100 => вклад в ATT1 18 баллов из 100, а в общий итог 5.4 балла из 100; `90/100 * 20% * 30% = 5.4`. Если пользователь получил `15/30` за midterm, то в ATT1 это 50% * вес midterm, а не «15%». Если ATT1=60, ATT2=80, то для цели 70 нужно Final >= (70 - 0.3*60 - 0.3*80)/0.4 = 70%. Проверяй дробные баллы, округление вверх к минимально достижимому целому point, недостающие оценки, неверные знаменатели, >100, требования отдельных порогов, несколько неизвестных, отсутствие course/syllabus, редактирование настроек и миграцию. Не объявляй итоговый результат достижимым, если отдельные подтверждённые требования силлабуса (например, минимальные аттестации или посещаемость) это запрещают. Если есть только предупреждение, выводи предупреждение, а не угадывай.
