# План сохранения стипендии

Планировщик расширяет существующие Study Calculator и Academic Dashboard.
Вкладка «Стипендия» открывается по умолчанию; «Обзор учёбы» сохраняет прежний экран.
Существующие пять силабусов и формула 30/30/40 не заменены.

## Правило и источник оценок

По предоставленному пользователем условию каждый учитываемый активный предмет
должен закончиться минимум на 70/100. В карточке можно изменить порог, личную цель
и участие предмета в сводке. Общий селектор 70/75/80/90/своя цель временно сравнивает
предметы с выбранным ориентиром. Числовое выполнение условия не гарантирует
стипендиальную выплату: допуск к экзаменам и прочие правила проверяются отдельно.

Подтверждённые значения берутся из сохранённых `academic_records` Moodle. Записи
других предметов/секций и mock-данные не используются. Оценка без числа или
известного положительного максимума остаётся `null`. Подтверждённый 0 отличается
от неизвестной оценки. Противоречивые дубли автоматически не выбираются.

Сохранённые ручные значения калькулятора остаются нетронутыми. Для ещё неизвестных
работ они могут выступать допущениями, если включён соответствующий переключатель.
Для подтверждённых работ планировщик использует свежую оценку Moodle; отличающееся
ручное значение остаётся в старом калькуляторе, и показывается пояснение.
Импорт в старом калькуляторе заполняет только пустые поля черновика при загрузке
и изменении оценок Moodle. Сохранение этого черновика остаётся явным действием.
Поэтому пустой сохранённый `calculator_values` не препятствует расчёту по реальным
оценкам: планировщик читает записи напрямую, без записи оценок обратно в Supabase.

## Формулы и ориентиры

`Final = ATT1 × 0.30 + ATT2 × 0.30 + Exam × 0.40`.

Для работы с весом `w%` внутри аттестации её вес в итоговой оценке равен `0.30 × w%`.
Для подтверждённых оценок `g_i` и итоговых долей `p_i`:

- Нижняя граница: `sum(g_i × p_i)`; оставшиеся работы предполагаются на 0.
- Верхняя граница: нижняя граница плюс весь оставшийся итоговый вес при 100.
- Требуемое взвешенное среднее: `(target − earned) / remaining_share`.
- Минимум конкретной работы при заданных остальных оценках:
  `(target − sum(other_score × other_share)) / work_share`.
- Абсолютный минимум конкретной работы предполагает 100 на всех остальных
  оставшихся работах. Это оптимистичная граница, а не практическая рекомендация.

Нижняя граница не превращает пустые оценки в фактические нули. Каждый ориентир
работы рассчитывается отдельно; одновременная подстановка всех минимумов не
обязана дать цель. Требуемые значения округляются вверх, итог отображается с двумя
знаками, а достижимость проверяется до округления. Для экзамена также показывается
минимальное целое число. Значения выше 100 явно указывают на недостижимость при
указанных допущениях.

Три независимых сценария изначально предполагают 50/70/90 на остаток. Можно
редактировать общие оценки по типам, индивидуальные допущения и неизвестные итоги
ATT1/ATT2. Например, при ATT2 = 80 подтверждённые компоненты сохраняются, а единое
значение оставшихся компонентов решается из весов. Если это потребовало бы оценок
вне 0–100, сценарий остаётся неизвестным и объясняет противоречие.

Кнопка «Все оставшиеся Assignments на 70» и одноимённый запрос ассистенту
задают ровно 70 для ещё не оценённых заданий. Конфликтующие индивидуальные
прогнозы заданий заменяются, итоговые допущения затронутых аттестаций снимаются:
итоги снова считаются по компонентам. Подтверждённые оценки и сохранённые ручные
значения калькулятора не изменяются. Вопрос ассистенту не сохраняет настройки.

Риск сводки оценивается по реалистичному сценарию; нехватка данных выделяется
отдельно. Недостижимость определяется верхней границей. Результат 70–74,99 имеет
малый запас, 75+ — больший числовой запас. Предупреждения допуска и расхождения
с официальными итогами также требуют внимания.

## Подтверждённое пользователем правило DBMS

Только для профиля DBMS / DMS52-EN:

| Moodle                                      | Компонент    | Вес внутри ATT1 |
| ------------------------------------------- | ------------ | --------------- |
| Assignment 1: 75/100                        | assignment_1 | 20%             |
| Assignment 2: 50/100                        | assignment_2 | 20%             |
| Assignment 3: 70/100                        | assignment_3 | 20%             |
| Lecture Async 1: 88/100                     | quiz_1       | 10%             |
| Quiz Midterm: 81/100                        | midterm      | 30%             |
| Calculated grade Register Midterm: 72.1/100 | сверка ATT1  | не добавляется  |

`75×0.2 + 50×0.2 + 70×0.2 + 88×0.1 + 81×0.3 = 72.1`.
`Lecture Async 2` аналогично связывается с `quiz_2`, если есть реальная оценка.
Async содержит готовый итог внешней образовательной платформы. Отдельные квизы
этой платформы не усредняются. Особые названия не применяются к другим силабусам.

Официальный Register используется для проверки рассчитанного ATT1, а не как
дополнительная работа. При расхождении показывается предупреждение. Явные записи
`ATT1` / `ATT2` с опубликованным итогом заменяют компоненты своего периода,
никогда не суммируются с ними. Не подставляйте в такой итог частично рассчитанный
агрегат незавершённого периода: это не подтверждённый итог всей аттестации.

Для пользовательских названий предусмотрено явное сопоставление одного готового
итога компонента или отдельных работ с подтверждёнными весами, суммой 100%.
Одна запись не может входить в два сопоставления. Взвешенное сопоставление не
допускает смешивания итогов с их компонентами. Сумма баллов относительно общего
максимума допустима только как явно подтверждённое правило конкретного курса.

Регрессионные примеры:

- DBMS: `72.1×0.30 + 80×0.30 + 61×0.40 = 70.03` (ATT2 гипотетическая).
- OS: `66.25×0.30 + 70×0.30 + 73×0.40 = 70.075`, отображение `70.08`.

## Приоритеты и интеграции

Приоритет учитывает доступный прирост итогового балла, близость известного дедлайна
и числовой дефицит предмета. +10 баллов за экзамен дают +4 к итогу. Неизвестные
дедлайны подписаны; неполная/устаревшая синхронизация не скрывается. Длительность
подготовки не оценивается, поэтому это не оптимизация баллов за час.

Сводка и приоритеты учитывают черновики карточек. Главная и Telegram используют
сохранённые настройки. При обновлении Moodle три сценария пересчитываются из
новых записей. TMA перечитывает учебные данные каждые 60 секунд и при возврате
в приложение; отдельная кнопка обновляет данные немедленно. Существующие workers,
аутентификация Moodle и шифрование сессий не изменены.

Assistant Brain получает READ-инструмент `study.scholarship`:

- «Как мне сохранить стипендию?»
- «Сколько нужно получить по DBMS?»
- «Что если все оставшиеся асики будут на 70?»
- «По какому предмету у меня самый большой риск?»
- «На какую работу стоит потратить больше всего времени?»

Ответы используют тот же чистый расчёт. Автоматические Telegram-рассылки не
включаются: ответы выдаются по запросу пользователя.

## Хранение и безопасное применение

Настройки хранятся отдельно в `study_courses.metadata.scholarship_planner_v1`.
Миграция не нужна. `study_calculator_v1`, прочая metadata и реальные оценки
сохраняются. Новый PUT `/api/tma/study/courses/:id/scholarship` использует
существующую проверку Telegram и активного пользователя; SELECT/UPDATE ограничены
`user_id`, ID и активным статусом. Вход ограничен схемой и лимитом тела сервера.
`expectedConfig` и CAS по `updated_at` возвращают 409 при конкурентном изменении,
не затирая чужую правку. Клиент сохраняет грязный черновик при обновлении данных.

Нет новых ключей, обходов авторизации, публичных SQL-функций или изменений RLS.
Ветка и рабочая копия изолированы от запущенных production-сервисов. Для релиза
после одобрения требуются обычные сборки и перезапуск бота; данные Moodle не нужно
перезаписывать или импортировать миграцией.
