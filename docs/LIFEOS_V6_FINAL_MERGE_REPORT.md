It matches [GHSA-6q48-6c7w-9gw2](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2), upstream severity **Critical**, alias `PYSEC-2026-4320`: affected emSign trust anchors associated with compromised intermediate CA keys. The observed version lies in the published affected range (`2019.03.09` through versions before `2026.10.18`). The maintainer's patched version is `2026.10.18`; [Python security guidance](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576) recommends certifi **2026.10.19** and pip **26.2.2** for the relevant CA coverage/compatibility. No package upgrade was performed.

Read-only host triage also found the `emSign ECC Root CA - G3` label in that installed version's standard bundle; the inspected certifi core does not reference a system CA bundle. The active `lifeos-lms-grades-worker.service` executable references the observed university environment, with no `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` or `SSL_CERT_FILE` key observed in its environment. This connects the observed environment to an active worker configuration, without establishing every worker's interpreter or each request's trust path. No TLS handshake, exploitation or actual interception was demonstrated; certificate contents, credential values and raw command arguments were not emitted. Downstream/per-request mitigation is not established by these observations. All worker requirements are unchanged from the original accepted baseline and use ranges; this is a **pre-existing host-environment finding, not a new V6 dependency regression**. Its pre-existing nature is not a critical-security waiver.

The fresh accepted #75 CI log independently resolved **certifi 2026.10.23**, newer than the upstream patch/recommendation. That patched hosted runner and its green application tests do not remediate the older existing host environment. The audit queried public package/version metadata without credentials or private payloads. It separately identified packaging-tool findings and vulnerable permitted lower-bound versions; permitted-version queries are not claims that those lower versions are installed. GHSA/PYSEC aliases are not counted as separate underlying vulnerabilities. A blanket “zero Python vulnerabilities” claim is unsupported. Fresh pnpm production and all-Node-dependency queries returned zero advisories at every severity (117 production / 323 total dependencies reported). The separate Python query covered 13 observed installed distributions and declared lower-bound examples; it found one certifi issue plus 11 alias-deduplicated packaging-tool issues. It is not a complete audit of every worker or CI resolver environment.
